## 背景

M1 的记忆只有 `candidate` 一个真实状态：`verified` 能写进文件，但没有任何东西检查它站不站得住。
审查 P1「记忆缺少可信生命周期」指的就是这个——重复记录容易被误认为可靠经验。

同时 `policy.Precedents.Verified` 是 `len(d.Evidence) > 0`，只要有人在 frontmatter 里
填一个 evidence ID 就成立，而那时 keel 根本不产生证据。

## 决定

证据只有一个产生入口：`keel verify` 真的 exec 一次验证器，把退出码翻译成 `pass/fail/error/timeout`，
写成 `.keel/evidence/E-<uuid>.md`。没有自述入口。

证据记两个摘要，回答两个不同的问题：

- `subject_digest` = 结论本身的摘要（不含 status / evidence / verified_at）。对不上 = 证据说的不是现在这条结论。
- `target.content_digest` = scope 覆盖的代码摘要。对不上 = 结论没变但代码变了，验证结果过期。

状态转换只有两个入口：`verify`（记忆 pass→verified、fail→disputed；决策只追加证据不改状态），
以及人手工编辑文件。**`check` 只推导并报告，不改写任何文件。**

## 备选与理由

- **让 `check` 自动把撑不住的 verified 改回 candidate**：省事，但 check 会在 pre-commit 里跑，
  等于提交时被静默改文件。状态转换必须留在 git diff 里能看见的地方。
- **只用一个 digest（结论或代码二选一）**：只盯结论就漏掉「代码变了」；
  只盯代码就漏掉「有人改了记忆正文却留着旧证据」。两种失效模式不同，必须分开报。
- **允许 `--trust self-reported` 登记一条人工审查结论**：看起来更灵活，
  但自述的通过既不能被别人重跑也不能被撤回，写进仓库就成了不可证伪的事实。真要记就写成 memory。
- **把 `subject_digest` 算上 status/evidence 字段**：直觉上更完整，实际会让 verify 自己写下的证据
  在下一次 check 时立刻失效——因为 verify 正好改了这两个字段。这是个死循环，digest_test.go 锁住了它。

## 后果与验证方式

`Precedents.Verified` 现在接的是真实证据，但它**只出现在 brief 的说明里，不参与上限计算**。
扩大自决范围仍然只能改配置——审查 P1-04 的行为没有因为证据模型上线而松动。

改记忆正文会让旧证据失效并报 error，这是有意的：结论变了就要重新验证。

验证：`go test ./internal/store/`（digest 契约）、`internal/cli/testdata/script/verify-*.txtar`
与 `memory-*.txtar`（端到端状态转换与推导）。`go test ./...` 必须全绿。
