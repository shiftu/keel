## 背景

模板更新的风险不是「更新失败」，是**悄悄覆盖掉本地演化**。用户改过的技能、
调过的策略，如果被模板新版盖掉，git 里看得见但人不会去看——他只会发现自己的改动没了。

## 决定

`.keel/template.yaml` 记每个导入文件在**导入当时**的摘要作为基线。
更新时三方比较 base / theirs / ours：只有本地没动过的才快进，两边都动过的一个字节都不写，
冲突文件的基线不推进——它会一直报到人处理为止。

`keel.yaml` 比的是配置的**含义**不是字节：两边都解码成配置结构、清掉 `tools`、再用同一个编码器写回。

## 备选与理由

- **模板优先覆盖**：正是要避免的失败模式。否决。
- **自动三方合并（像 git merge）**：keel 处理的是 YAML frontmatter 和 Markdown 正文，
  行级合并会产出语法上合法但语义上错误的规则文件。报冲突让人来判断更诚实。否决。
- **只清 `tools` 不做配置规范化**：试过，第一次 `update` 就把「什么都没改」报成冲突——
  `init` 写本地配置时是把结构体序列化出去的，字段顺序跟模板手写的那份对不上。

## 后果与验证方式

`local-deleted` 与 `template-deleted` 每次都会重复报告且退出码仍是 0：
两个方向 keel 都不替人做主。这是噪音，但比替人删文件好。

验证：`internal/cli/testdata/script/template-update.txtar` 覆盖全部六种处置，
断言冲突文件本地内容原样、模板那段没进来，且冲突基线不推进（第二次 dry-run 仍然报）。
