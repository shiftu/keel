# 受控进化

## 什么时候触发

只在**显式的维护任务**或**有边界的收尾**里跑。不要在每次普通任务后自动展开。

## 步骤

1. **读报告。**

   ```
   keel review --json
   ```

   报告里的次数**只决定审阅优先级**，不决定可信或生效。同一个错误被转述三次不是三份证据。

2. **处理到期决策。** `review_after` 到了的决策，按实际证据改状态并在正文末尾写一句原因：

   - 有相关验证证据且没有反例 → 可以提议转 `proven`
   - 出现过 revert 或派生规则持续失败 → 转 `revisit`
   - 你自己写的 proven 不构成独立验证，不要用它去换更高的自决上限

3. **处理学习候选。** 每批限量，不要无限扩展：

   - 多条同主题记忆指向同一条不变量 → 提炼成规则，**默认 `candidate`**，附 `check.argv`
   - 一条规则反复把人拦住 → 说明「该怎么做」比「不许怎么做」更有用，写成技能
   - 一条可靠事实可以长期只是事实，不必逐级变成技能

4. **对照验证。** 新硬规则至少要有三个用例：一个应该通过、一个应该失败、一个边界。
   验证器由现行基线提供 —— 候选不能通过放宽自己的检查来宣告通过。

   `check.argv` 的退出码约定：`0` 通过，`1` 发现违规，**其余一律是 error**。
   目录不存在、工具没装都必须是 error，绝不能写成「通过」。

5. **按策略生效或撤回。**

   - 补来源、去重、通过验证的事实：可在预授权范围内直接维护
   - 新增硬规则、改变项目约束、扩大工作流上限：走项目既有审查，不由候选自我批准
   - 发现反例或回归：标 `disputed` / `retired`，恢复对应旧规则，**不要删除失败历史**

6. **收尾。**

   ```
   keel check --target worktree
   keel sync
   ```

   一次提交，说明这批改了几条、依据是什么。

## 处理失效条目

`object_stale` 说明 scope 指向的路径已经不在了。先重定位；确实过时就归档，保留原因，不要直接删掉历史解释。
